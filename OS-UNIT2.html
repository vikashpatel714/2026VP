LECTURE NOTES — UNIT · PROCESS & CPU SCHEDULING

How an operating system decides who runs next

A process is born, waits its turn, runs, sometimes waits again, and dies — and every one of those transitions is a decision the kernel has to make, thousands of times a second. These notes walk through that decision machinery: processes and their control blocks, the schedulers that move work between queues, the classic CPU-scheduling algorithms with worked numericals, and how threads let a single process do more than one thing at once.

01 / PROCESS MANAGEMENT

What a process is, and how the kernel tracks it

A program is a passive file sitting on disk — instructions and data, nothing more. The moment you run it, the OS loads it into memory, gives it a private address space and a process ID, and it becomes a process: a program in execution, with a state that changes constantly as the CPU is handed around.

The process and its address space

Every process owns a logical address space divided into four regions. Reading from the low addresses upward:

Text is fixed at load time; the stack and heap grow toward each other at run time.

Text section

The compiled instructions of the program. Shared and read-only, so two users running the same binary can share one copy in memory.

Data & heap

Data holds global/static variables fixed at compile time. The heap is memory the program requests at run time (malloc, new) and must release itself.

Stack

Holds temporary data per function call: parameters, return address, local variables. Pushed on call, popped on return.

Program counter & registers

Not part of the address space, but part of the process's execution context — where it is in the code, and what its CPU registers hold right now.

The five-state transition diagram

At any instant a process is in exactly one of five states. Press play to step a process through a realistic lifecycle — each move is explained as it happens.

StateMeaning

Process Control Block (PCB)

The PCB is the data structure the kernel keeps per process — a repository of everything the OS needs to know to pause it and resume it later exactly where it left off. Every context switch is really the kernel saving one PCB and loading another.

On a context switch the kernel writes the outgoing process's live register values into its PCB, then reloads the incoming process's PCB into the registers.

Long-term, mid-term and short-term schedulers

A process crosses several queues on its way to the CPU. Three different schedulers control those crossings, and they run at very different frequencies.

Long-term admits jobs, short-term picks who runs next, medium-term swaps processes out to ease memory pressure.
RUNS RARELY

Long-term scheduler

Also called the job scheduler. Selects which jobs are admitted from the disk job pool into the ready queue, controlling the degree of multiprogramming. Runs seconds-to-minutes apart, so it can afford to be slow and careful — it decides the process mix (CPU-bound vs I/O-bound).

RUNS OCCASIONALLY

Medium-term scheduler

Handles swapping: temporarily removes a process from memory to disk to reduce the degree of multiprogramming, then reintroduces it later. Improves the process mix and frees memory under pressure.

RUNS CONSTANTLY

Short-term scheduler

Also called the CPU scheduler. Picks one process from the ready queue and dispatches it to the CPU — invoked every few milliseconds, so it must be extremely fast. This is the scheduler the rest of this page is about.

02 / CPU SCHEDULING

Choosing who runs next

Whenever the CPU goes idle, the short-term scheduler must pick a process from the ready queue. The algorithm it uses changes everything: average wait time, responsiveness, and whether short jobs get stuck behind long ones. Every algorithm below uses the same two derived numbers, so pin these down first.

TURNAROUND TIME

Completion time − Arrival time. Total time a process spends in the system, from arrival to finish — including all its waiting.

WAITING TIME

Turnaround time − Burst time. Time spent sitting in the ready queue, not actually executing.

Preemptive vs non-preemptive

Non-preemptive

Once a process is given the CPU, it keeps it until it finishes or voluntarily blocks for I/O. The scheduler only acts when the running process leaves the CPU on its own. Simple, low overhead — but a long process can make everything behind it wait (the convoy effect).

Preemptive

The scheduler can forcibly suspend a running process — e.g. because a newly arrived process is "more urgent" — and give the CPU to someone else. Fairer and more responsive, but every switch costs a context-switch overhead, and shared data needs careful synchronization.

First Come, First Served (FCFS)

NON-PREEMPTIVE Processes are served strictly in arrival order, using a plain FIFO queue. It's the simplest possible policy — and the one most vulnerable to the convoy effect: one long CPU-bound process at the front makes every short process behind it wait far longer than its own burst time would suggest.

Shortest Job First (SJF)

NON-PREEMPTIVE Among the processes currently in the ready queue, always pick the one with the smallest CPU burst. SJF is provably optimal for minimizing average waiting time when all jobs are available together — but it needs to know burst times in advance, which in practice means predicting them (e.g. by exponential averaging of past bursts), and it can starve long processes if short ones keep arriving.

Numerical. Same three processes as above, now scheduled shortest-first.

Waiting time: P2 = 0, P3 = 3, P1 = 6 → average = 3. Turnaround: 3, 6, 30 → average = 13. Same processes, same total work — but average waiting fell from 17 to 3 purely by reordering.

Shortest Remaining Time First (SRTF)

PREEMPTIVE The preemptive cousin of SJF. Whenever a new process arrives, compare its burst time against the remaining time of the process currently running — if the newcomer is shorter, preempt immediately. This reacts well to short jobs arriving late but adds context-switch overhead and can still starve long jobs.

Priority Scheduling

Each process carries a priority number (by convention, lower number = higher priority); the CPU goes to the highest-priority ready process. It comes in both flavours:

NON-PREEMPTIVE

Priorities are only compared when the CPU is free — a running process is never interrupted even if something more urgent arrives.

PREEMPTIVE

A newly arrived process with higher priority immediately preempts whatever is running, exactly like SRTF but comparing priority instead of remaining time.

Both variants share a real weakness: indefinite blocking (starvation) — a low-priority process can wait forever if a steady stream of higher-priority work keeps arriving. The standard fix is aging: gradually raise the priority of a process the longer it waits, guaranteeing it eventually becomes the highest priority in the queue.

Round Robin (RR)

PREEMPTIVE Designed for time-sharing systems. Every process gets a fixed slice of CPU time — the time quantum — in a circular queue; if it hasn't finished when the quantum expires, it's preempted and sent to the back of the queue. No process waits more than (n−1) × quantum for its next turn, which makes RR excellent for responsiveness. The quantum is a real trade-off: too large and it degenerates into FCFS; too small and context-switch overhead dominates.

Multilevel Queue Scheduling

Real systems often have process categories that genuinely need different treatment — an interactive foreground process versus a batch background job. Multilevel queue scheduling partitions the ready queue into several separate queues, each with its own scheduling algorithm, and processes are permanently assigned to one queue based on a property like process type or priority.

Between-queue scheduling is usually strict priority (a lower queue runs only when every queue above it is empty), sometimes with time slicing across queues.

The weakness is rigidity: a process assigned to the batch queue stays there forever, even if its behaviour changes — it can starve indefinitely if higher queues are never empty.

Multilevel Feedback Queue Scheduling

MLFQ fixes that rigidity by letting processes move between queues based on observed behaviour. It's the closest a scheduler gets to learning about a process:

  • A new process enters the topmost queue, which has the smallest time quantum.
  • If it uses its whole quantum without finishing (behaves like a CPU-bound job), it's demoted to a lower queue with a longer quantum.
  • If it blocks for I/O before its quantum expires (behaves like an interactive job), it's kept at the same level or promoted.
  • To prevent starvation, processes are periodically promoted back up if they've been waiting too long — the scheduler's own version of aging.
A short interactive burst never leaves Queue 0; a long CPU-bound job sinks toward FCFS — but aging pulls it back up before it starves.

MLFQ is defined by its parameters: the number of queues, the quantum at each level, the promotion/demotion rule, and how a process is initially assigned. Because it reacts to observed behaviour instead of a fixed label, it's the most general scheduling algorithm — and the one most real operating systems (including Windows and historically Solaris) actually approximate.

03 / THREADS

One process, many threads

A process is the unit of resource ownership — its address space, open files, and permissions. A thread is the unit of CPU scheduling within that process: its own program counter, register set, and stack, but sharing the process's address space and resources with every other thread in it.

Process vs thread

Threads duplicate only what must be private (registers, stack, PC); everything else in the process is shared automatically.

Thread states

A thread's lifecycle mirrors a process's, minus the memory-allocation weight of New/Terminated:

Runnable → Running is the scheduler's doing; Running → Blocked happens when the thread requests I/O or waits on a lock; Blocked → Runnable happens when that event completes.

Why bother with threads

Responsiveness

An application can keep responding to the user even while part of it is blocked — e.g. a UI thread stays interactive while a background thread loads a file.

Resource sharing

Threads share the address space by default, so passing data between them is just accessing shared memory — no IPC needed.

Economy

Creating and context-switching a thread is far cheaper than doing the same for a whole process, since most of the state is already shared.

Scalability

On a multicore machine, threads of one process can genuinely run in parallel on different cores, not just interleaved on one.

User-level vs kernel-level threads

User-level threads

Managed entirely by a thread library in user space; the kernel doesn't know they exist — it sees one process. Creation and switching are fast (no system call), but if one thread makes a blocking system call, the entire process blocks, and they can't be scheduled onto separate cores.

Kernel-level threads

Managed and scheduled directly by the OS kernel, which is aware of each one individually. A blocking call in one thread doesn't stall the others, and they can run in true parallel across cores — at the cost of higher creation/switching overhead, since each op needs a system call.

Multithreading models

These describe how user-level threads are mapped onto kernel-level threads.

Many-to-One

Many user threads map to a single kernel thread. Fast, portable — but one blocking call freezes every thread, and there's no real parallelism.

One-to-One

Each user thread gets its own kernel thread. True parallelism, one block doesn't stall the rest — but creating a thread means creating a kernel thread too, so it's heavier. Used by Linux and modern Windows.

Many-to-Many

Many user threads multiplex over a smaller or equal number of kernel threads — the OS can create as many kernel threads as needed. Combines the flexibility of many-to-one with real parallelism.

Hyper-Threading

Hyper-Threading (Intel's name for simultaneous multithreading, SMT) lets one physical core present itself to the OS as two logical processors. It duplicates only the architectural state needed to track two independent instruction streams — registers, program counter — while the core's actual execution units, caches, and pipeline are shared and interleaved between them.

The OS scheduler sees two CPUs and can run two threads "at once" — but they're still sharing one core's actual execution hardware.

The payoff: while one logical thread stalls waiting on memory (a cache miss), the core's execution units aren't idle — they can issue instructions from the other logical thread instead. It improves throughput on mixed workloads, typically by roughly 15–30% in practice, but it is not the same as having two real cores — if both threads are heavily competing for the same execution units or cache, the gain shrinks or can even go negative.
