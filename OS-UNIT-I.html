LECTURE NOTES — OS FUNDAMENTALS & LINUX SHELL SCRIPTING

From the kernel's first interrupt to a script that runs itself at 2 a.m.

Every operating system, from a 1950s batch machine to the phone in your pocket, solves the same problem: sit between messy hardware and demanding programs, and make the whole thing feel orderly. These notes trace that idea from the earliest generations of OS design, through interrupts and system calls, into the one OS you can actually open a terminal on right now — Linux — and out the other side into shell scripts that do a sysadmin's job while they sleep.

01 / FUNDAMENTALS OF OPERATING SYSTEMS

What an operating system actually does

Strip away the marketing and an OS has one job: manage hardware resources — CPU, memory, storage, I/O devices — on behalf of programs that don't know or care about each other, while presenting a clean, consistent interface to both the programs and the person using them. Think of a busy hospital: doctors (programs) need beds, equipment and staff (hardware), and the hospital administration (the OS) is what prevents chaos — scheduling who gets the operating theatre when, without any doctor having to negotiate directly with another.

The OS is the only layer that touches both raw hardware and every running program — that's why it's a single point of control.

Resource manager

Decides which process gets the CPU, which pages sit in RAM, and in what order disk requests are served — arbitrating between programs that would otherwise fight over the same hardware.

Abstraction provider

Gives programs a clean file, a virtual address space, and a socket — instead of forcing every application to speak directly to disk sectors and network cards.

Control program

Prevents errors and improper use — stopping one process from reading another's memory, or from monopolising the CPU forever.

Generations of operating systems

OS design tracks hardware generations closely — each leap in electronics unlocked a fundamentally different way of managing a computer.

click a generation to read what changed

1st Generation (1940s–1950s)

Vacuum tubes and plugboards. There was no operating system at all — a single program had the entire machine, wired by hand with cables and switches. Programming meant physically rewiring the computer.

Operating system architecture

How the OS itself is internally organised is a design choice with real consequences for performance, reliability and extensibility. Four broad styles:

Monolithic architecture

All services run in kernel mode inside one address space — fast (direct function calls between modules) but a bug in one driver can crash the whole OS. Traditional UNIX and the Linux kernel follow this style.

Layered architecture

Each layer only calls the layer directly beneath it, hiding its own details from the layers above — easier to debug and verify, at the cost of extra call overhead between layers.

Microkernel architecture

Only the bare essentials — inter-process communication and basic scheduling — live in kernel mode; file systems, drivers, and network stacks run as ordinary user-space servers reached via message passing. Used by QNX and MINIX; more robust to a single driver crashing, but message-passing overhead costs performance.

Hybrid architecture

Most production systems compromise: a kernel that is mostly monolithic for performance but exposes some services in a microkernel-like modular way. Windows NT and macOS's XNU kernel are the standard examples — monolithic-style device drivers and file systems for speed, with modular loadable components for flexibility.

Interrupt handling

An interrupt is hardware's way of tapping the CPU on the shoulder: "stop what you're doing, something needs attention." Instead of the CPU constantly polling every device to ask "are you done yet?" (wasteful), devices simply raise a signal when they need service, and the CPU reacts.

Press "Trigger interrupt" to see a keyboard interrupt walk through the full cycle.

Hardware interrupts

Raised by physical devices — a key pressed, a network packet arriving, a disk finishing a read — via a dedicated interrupt request (IRQ) line.

Software interrupts (traps)

Raised deliberately by a running program — a system call, or an error like division by zero — to hand control to the kernel on purpose.

Every interrupt has a unique number that indexes into the interrupt vector table, a fixed array of addresses the CPU consults to jump straight to the correct interrupt service routine (ISR) — no searching required, which is why interrupt response can be fast and deterministic. Some interrupts are maskable (the CPU can temporarily ignore them during a critical section); a non-maskable interrupt (NMI) — reserved for catastrophic events like a hardware memory failure — cannot be ignored.

System calls and the kernel

A CPU runs in one of (at least) two privilege levels: user mode, where ordinary programs run and cannot directly touch hardware or other processes' memory, and kernel mode, where the OS runs with full hardware access. A hardware mode bit tracks which one is active. A system call is the only sanctioned door between them — the mechanism a user program uses to politely ask the kernel to do something privileged on its behalf, like opening a file or creating a process.

read() looks like an ordinary function call to the programmer — underneath, it traps into the kernel and back.
1. Program calls read() — a normal-looking function in user mode.
2. Library executes a trap instruction — mode bit flips to kernel.
3. Kernel's syscall handler does the actual privileged work.
4. Mode bit flips back — program resumes in user mode with the result.

Types of operating systems

EARLIEST

Batch Operating System

Jobs with similar needs are grouped ("batched") and fed to the computer together with no interaction while running; an operator loads a stack of jobs and the results come out later, all at once. No user waits at a screen — the computer decides the order and simply works through the pile.

Real-life example: a bank's overnight batch job that processes every account's interest calculation and prints statements for all customers in one run, or exam-result processing where thousands of scripts are graded in one scheduled pass.

KEEP THE CPU BUSY

Multiprogramming OS

Several programs are kept in memory at once so that when one is blocked waiting for I/O, the CPU immediately switches to another instead of sitting idle. The goal is maximum CPU utilization, not necessarily fast response to any one user.

Real-life example: a university server that simultaneously runs a print job, a database query, and a compile job — while the compile waits on disk reads, the CPU quietly keeps the database query moving.

FAST SWITCHING

Multitasking OS

Extends multiprogramming with fast enough time-sharing that it feels simultaneous to a human — the CPU rapidly switches between tasks, giving each a tiny time slice. This is what makes an interactive desktop or phone possible at all.

Real-life example: playing music, typing a document, and downloading a file on your laptop at the same time — the CPU is really only doing one thing at any instant, switching so fast you never notice.

MORE THAN ONE CPU

Multiprocessor OS

Manages a machine with two or more CPUs sharing memory and peripherals, either running processes in true parallel (not just interleaved) or splitting one workload across cores. Offers higher throughput and can survive a single processor failing (graceful degradation).

Real-life example: a data-center server handling millions of search queries by spreading them across dozens of CPU cores simultaneously.

DEADLINES ARE THE POINT

Real-Time Operating System (RTOS)

Correctness depends not just on the right answer but on delivering it within a strict, predictable time bound. A hard real-time system fails completely if a deadline is missed; a soft real-time system just degrades in quality.

Real-life examples: a car's anti-lock braking system and a hospital pacemaker are hard real-time — missing a deadline by milliseconds can be fatal. Video streaming and voice calls are soft real-time — a dropped or delayed frame is annoying, not catastrophic.

02 / SHELL SCRIPTING IN LINUX

Linux: an OS you can actually open up

Linux is a concrete, everyday example of most of the ideas above: a monolithic-style kernel, a strict user/kernel mode boundary, system calls, and a rich set of process types all running under one roof. What makes it special for learning is that the interface to all of it — the shell — is just a program you can type into.

The shell isn't the kernel — it's an ordinary program that reads what you type and turns it into system calls on your behalf.

Every command you type — ls, cp, grep — is itself just a small program. The shell's job is to find it, run it (which under the hood is a fork() + exec() pair of system calls), wire up its input/output, and wait for it to finish.

Shell variables

A shell variable holds a piece of text. No dollar sign when you set it, but always a dollar sign when you read it back — that distinction trips up almost every beginner.

#!/bin/bash
name="Operating Systems"    # set — no $, no spaces around =
version=2

echo "Course: $name (Unit $version)"   # read — with $

Variables can also come from a command's output using command substitution, written $(command) — for example today=$(date +%F) stores today's date as text. Wrap a variable in quotes ("$name") whenever it might contain spaces, to stop the shell from splitting it into separate words.

Control structures

Conditionals — if / elif / else

#!/bin/bash
usage=93
if [ $usage -gt 90 ]; then
  echo "Warning: disk almost full!"
elif [ $usage -gt 70 ]; then
  echo "Notice: disk usage getting high."
else
  echo "Disk usage normal."
fi

Square brackets [ ... ] are actually a command (test) that checks a condition and exits successfully or not; -gt, -lt, -eq compare numbers, while = and != compare text.

Loops — for, while, until

#!/bin/bash
for i in 1 2 3 4 5
do
  echo "Processing file_$i.log"
done
echo "All files processed."

A while loop keeps going as long as its condition stays true — useful when you don't know the count in advance, like reading a file line by line or waiting for a resource to free up. until is the mirror image: it repeats until the condition becomes true.

The case statement is a cleaner alternative to a long chain of elifs when you're matching one variable against several fixed patterns — commonly used to parse a command-line option:

case $1 in
  start)   echo "Starting service..." ;;
  stop)    echo "Stopping service..." ;;
  restart) echo "Restarting service..." ;;
  *)       echo "Usage: $0 {start|stop|restart}" ;;
esac

Functions

A function packages a block of commands under a name, so a script can call it — with different inputs — instead of repeating itself. Inside a function, $1, $2… refer to the arguments it was called with, and local keeps a variable from leaking into the rest of the script.

#!/bin/bash
count_down() {
  local n=$1
  while [ $n -gt 0 ]; do
    echo "T-minus $n"
    n=$((n-1))
  done
  echo "Liftoff!"
}
count_down 3
03 / CASE STUDY

Automating system administration with a shell script

This is the real payoff of everything above: a script that does a sysadmin's repetitive nightly checklist — check disk space, back up important data, delete old backups, log who's online — without a human ever typing a command. It combines variables, functions, a conditional, command substitution, and a loop-free but iteration-friendly command (find) into one coherent tool.

#!/bin/bash
# auto_admin.sh — daily system maintenance script

LOGFILE="/var/log/auto_admin.log"
BACKUP_DIR="/backup"
SRC_DIR="/home/user/data"
THRESHOLD=80

timestamp() { date "+%Y-%m-%d %H:%M:%S"; }
log() { echo "[$(timestamp)] $1" >> "$LOGFILE"; }

# 1. Check disk usage
usage=$(df / | tail -1 | awk '{print $5}' | tr -d '%')
if [ "$usage" -ge "$THRESHOLD" ]; then
  log "WARNING: Disk usage at ${usage}% (threshold ${THRESHOLD}%)"
else
  log "Disk usage OK at ${usage}%"
fi

# 2. Back up important data
mkdir -p "$BACKUP_DIR"
tar -czf "$BACKUP_DIR/backup_$(date +%F).tar.gz" "$SRC_DIR"
log "Backup completed: backup_$(date +%F).tar.gz"

# 3. Delete backups older than 7 days
find "$BACKUP_DIR" -name "*.tar.gz" -mtime +7 -exec rm {} \;
log "Old backups cleaned up"

# 4. Report how many users are logged in
users_online=$(who | wc -l)
log "Active users: $users_online"

echo "Maintenance run complete. See $LOGFILE for details."

Reading it line by line

  • Variables at the top (LOGFILE, BACKUP_DIR, THRESHOLD) put every configurable value in one place — change the threshold once, not everywhere it's used.
  • Two small functions (timestamp, log) avoid repeating the same date formatting and file-append logic four times.
  • Command substitution + a pipeline (df / | tail -1 | awk … | tr -d '%') turns raw disk-usage output into a single clean number the if can compare.
  • tar compresses the whole source directory into one dated archive — a new file every day, never overwriting yesterday's.
  • find ... -mtime +7 -exec rm finds every backup older than 7 days and deletes it — this is what stops backups from silently filling the disk forever.
  • who | wc -l is a one-line pipe: list logged-in users, count the lines.

$ ./auto_admin.sh

Making it run itself: cron

A script is only "automated" once nobody has to remember to run it. Linux's cron daemon runs any command on a fixed schedule, defined by a single line in a user's crontab:

This entry runs auto_admin.sh at 02:00 every single day — five fields for minute, hour, day-of-month, month, day-of-week, each "*" meaning "every".

Add it with crontab -e, and the operating system itself — through cron, one of its own background processes — becomes the thing that remembers to keep the system healthy. That closes the loop back to where these notes started: an OS is fundamentally a resource manager, and a well-placed shell script is just one more resource it's willing to manage on a schedule.
