Why processes need synchronization

Processes that cooperate usually share something: a variable, a file, a printer, a bank balance. When two of them touch that shared thing at the same moment, the result depends on who happens to run first. That uncertainty is called a race condition, and process synchronization is the set of techniques that removes it.

In real life: Two friends book the last cinema seat on two different apps at the same second. Both apps check "seat free?", both see yes, both confirm. One seat, two tickets. The apps did not fail individually; they failed because "check" and "book" were not one indivisible action.

Key vocabulary

  • Critical section (CS): the part of a program that reads or writes shared data. Only one process should be inside at a time.
  • Entry section: the code that asks for permission to enter the critical section.
  • Exit section: the code that gives the permission back.
  • Remainder section: everything else the process does; it does not touch shared data.
  • Busy waiting (spinning): looping on a condition and burning CPU time until it becomes false.

The three requirements of a correct solution

  1. Mutual exclusion. If one process is inside the critical section, no other process may be inside.
  2. Progress. If the critical section is empty and some processes want to enter, only those processes take part in choosing who goes next, and the choice cannot be postponed forever. A process sitting in its remainder section must never block others.
  3. Bounded waiting. Once a process has asked to enter, there is a limit on how many times others may enter before it. No starvation.

A good solution must also make no assumption about CPU speed or the number of processors.

How the solutions are grouped

Software (busy waiting): lock variable, strict alternation, Peterson, BakeryHardware support: test and set lockOS or language support: semaphores, monitors

Feel the race condition

The statements counter++ and counter-- look like one step, but the CPU runs each as three: load into a register, change the register, store it back. Run the unlucky schedule and watch one update vanish.

Remember for the exam

  • A race condition exists when the outcome depends on the order in which processes are scheduled.
  • The three conditions are mutual exclusion, progress and bounded waiting. Learn them word for word.
  • Busy-waiting solutions waste CPU cycles; semaphores and monitors block the process instead.

1Lock variable

The simplest idea: keep one shared flag called lock. Zero means the critical section is free, one means someone is inside. Check it, set it, enter.

Software solutionMultiprocessBusy waiting

In real life: A public restroom with an "Occupied" sign on the door. It works well when people walk up one at a time. The trouble starts when two people reach the door together, both see "Vacant", and both push the door before either flips the sign.

shared int lock = 0;            // 0 = free, 1 = busy

while (true) {
    while (lock == 1) ;            // entry: wait until free
    lock = 1;                     // entry: take the lock
    /* CRITICAL SECTION */
    lock = 0;                     // exit: release
    /* REMAINDER SECTION */
}

Why it breaks

Reading lock and writing lock are two separate machine instructions. The scheduler can pause a process between them. A second process then reads the same stale value of 0, and both walk in. The lock variable is itself a shared resource, and nothing is protecting it.

✘Mutual exclusionFails when a context switch lands between check and set.
✔ProgressA process in its remainder section never blocks another.
✘Bounded waitingNothing stops a process from losing again and again.

Remember for the exam

  • Lock variable is a software, multiprocess solution that does not guarantee mutual exclusion.
  • The flaw is non-atomic test-then-set. Fixing that needs hardware help (test and set lock).

2Strict alternation

Instead of a free/busy flag, use a turn variable that says whose turn it is. Process 0 may enter only when turn == 0; on leaving it hands the turn to process 1, and vice versa.

Software solutionTwo processes onlyBusy waiting

In real life: Two siblings sharing one gaming console with the rule "you play, then I play, then you play, strictly in turns". It is perfectly fair, until one sibling goes out for the evening. The other one now sits idle next to a free console, because it is not their turn.

shared int turn = 0;

// Process Pi  (i = 0 or 1)
while (true) {
    while (turn != i) ;            // entry: wait for my turn
    /* CRITICAL SECTION */
    turn = 1 - i;                 // exit: pass the turn
    /* REMAINDER SECTION */
}

Why it fails the progress test

The processes are forced to enter in the pattern P0, P1, P0, P1. If P0 is slow in its remainder section, P1 finishes its turn, gives the turn to P0, and then cannot enter again even though the critical section is empty. The speed of the whole system becomes the speed of the slowest process.

✔Mutual exclusionOnly the process whose turn it is can pass.
✘ProgressA process outside the CS can block one that wants in.
✔Bounded waitingThe other process can enter at most once before you.

Remember for the exam

  • Strict alternation guarantees mutual exclusion but violates progress.
  • It works for exactly two processes and forces them to alternate.
  • It is also called a spin lock because of the empty while loop.

3Peterson's solution

Peterson combined the two earlier ideas. Each process announces its interest with a flag, and a shared turn variable decides who waits if both are interested at the same time.

Software solutionTwo processesBusy waiting

In real life: Two polite people reach a narrow doorway together. Each raises a hand ("I want to go through") and says "after you". Whoever said "after you" last is the one who ends up waiting. If only one of them is interested, they simply walk through.

shared boolean flag[2] = {false, false};
shared int     turn;

// Process Pi, with j = 1 - i
while (true) {
    flag[i] = true;               // I am interested
    turn = j;                     // but you may go first
    while (flag[j] && turn == j) ;  // wait only if j is interested AND it is j's turn
    /* CRITICAL SECTION */
    flag[i] = false;              // no longer interested
    /* REMAINDER SECTION */
}

Why mutual exclusion holds

  1. For both processes to be inside, each must have passed its own while test.
  2. Both flags are true at that time, so each test could only pass because turn pointed to itself.
  3. But turn holds one value only. It cannot equal 0 and 1 together, so at most one test can pass.

Progress and bounded waiting also hold: a process outside the CS has its flag false and cannot block anyone, and the waiting process gets in after at most one entry by the other process.

✔Mutual exclusionThe single turn variable breaks every tie.
✔ProgressOnly interested processes affect the decision.
✔Bounded waitingWaits for at most one entry by the other process.

Limits. It works for two processes only, it busy-waits, and on modern CPUs that reorder memory operations it needs memory barriers to stay correct. That is why real systems use hardware atomic instructions instead.

Remember for the exam

  • Peterson's solution satisfies all three requirements, for two processes.
  • Order matters: set flag[i] first, then turn. Swapping them breaks mutual exclusion.
  • The process that writes turn last is the one that waits.

4Lamport's bakery algorithm

Peterson handles two processes. Lamport's bakery algorithm handles N. Every process takes a numbered ticket before entering, and the holder of the smallest ticket goes first, exactly as in a busy bakery or a bank.

Software solutionN processesBusy waiting

In real life: A sweet shop with a token machine. You pull a ticket, watch the counter display, and wait until your number is the lowest one still holding a ticket. If two customers press the machine at the same instant and get the same number, the shop breaks the tie with something fixed, such as their membership ID.

shared boolean choosing[n] = {false};   // "I am picking a ticket right now"
shared int     number[n]   = {0};       // ticket number, 0 = no ticket

// Process Pi
choosing[i] = true;
number[i]   = 1 + max(number[0], ..., number[n-1]);
choosing[i] = false;

for (j = 0; j < n; j++) {
    while (choosing[j]) ;                                   // wait while Pj is picking
    while (number[j] != 0 && (number[j], j) < (number[i], i)) ;  // wait for smaller tickets
}
/* CRITICAL SECTION */
number[i] = 0;                                          // tear up the ticket

The three ideas to understand

  1. Ticket = 1 + maximum. Later arrivals normally get bigger numbers, so the order of service is the order of arrival (first come, first served).
  2. Ties are possible. Two processes can read the same maximum at the same moment. The pair comparison (number[j], j) < (number[i], i) compares tickets first and, if equal, the process ids. The smaller id wins.
  3. The choosing array. Without it, a process could compare against a ticket that is still being computed and wrongly decide it has the smallest one. Waiting while choosing[j] is true closes that gap.
✔Mutual exclusionThe smallest (ticket, id) pair is unique.
✔ProgressOnly competing processes are compared.
✔Bounded waitingFirst come, first served: at most N-1 processes go ahead.

Drawbacks. Ticket numbers can grow without bound, every entry scans all N processes, and it still busy-waits. It remains famous because it needs no special hardware and works even when reads and writes are not atomic.

Remember for the exam

  • Bakery is a software solution for N processes and satisfies all three requirements.
  • Tie-breaking rule: smaller ticket first, and if equal, smaller process id first.
  • Arrays used: choosing[n] (boolean) and number[n] (integer).

5Test and set lock (TSL)

The lock variable failed because "check" and "set" were two steps. Test-and-set is a hardware instruction that does both in a single, indivisible (atomic) step: it returns the old value and sets the variable to true, and no other CPU or interrupt can slip in between.

Hardware solutionN processesBusy waiting (spin lock)

In real life: A turnstile at a metro gate that checks your token and locks behind you in one push. Two people cannot both pass on the same token, because there is no gap between "checking" and "locking". The same idea appears in a hotel key-card door: unlocking and marking the room as occupied happen in one action.

// Executed atomically by the hardware
boolean TestAndSet(boolean *target) {
    boolean old = *target;
    *target = true;
    return old;
}

shared boolean lock = false;

while (true) {
    while (TestAndSet(&lock)) ;       // returns true if someone already holds the lock
    /* CRITICAL SECTION */
    lock = false;                    // exit
    /* REMAINDER SECTION */
}

How it works

  1. The lock starts as false (free).
  2. The first process calls TestAndSet. It gets false back, and the lock is now true. It exits the loop and enters.
  3. Every other process gets true back, so it keeps spinning.
  4. On exit, the process sets the lock back to false and one spinning process wins the next call.
✔Mutual exclusionAtomic read-and-set leaves no gap.
✔ProgressFree lock means someone can take it.
✘Bounded waitingWho wins the race is arbitrary, so starvation is possible.

Improving it. Bounded waiting can be added with a waiting[n] array so that an exiting process hands the lock to the next waiting process in cyclic order. Related atomic instructions are Swap and Compare-and-Swap. Spin locks suit very short critical sections on multiprocessors; for long waits, blocking (semaphores) is kinder to the CPU.

Remember for the exam

  • TSL guarantees mutual exclusion and progress but not bounded waiting.
  • It is atomic because the hardware locks the memory bus for the duration of the instruction.
  • It works for any number of processes and wastes CPU through busy waiting.

6Semaphores

Introduced by Edsger Dijkstra in 1965, a semaphore is an integer variable that can be changed only through two atomic operations: wait(S) (also written P or down) and signal(S) (also written V or up). Unlike the earlier methods, a process that cannot proceed is put to sleep in a queue instead of spinning, so no CPU is wasted.

OS-level toolN processesBlocking, no busy waiting

wait(S) {                      // P, down
    S = S - 1;
    if (S < 0) {
        add this process to S.queue;
        block();               // go to sleep
    }
}

signal(S) {                    // V, up
    S = S + 1;
    if (S <= 0) {
        remove a process P from S.queue;
        wakeup(P);
    }
}

A useful reading of the value: when S is positive it counts free resources; when S is negative, its absolute value is the number of sleeping processes.

In real life: A parking lot displays "Free slots: 3". Each arriving car decrements the count (wait); each departing car increments it (signal). When the display shows 0 the barrier stays down and new cars queue outside, asleep with their engines off. When a car leaves, exactly one waiting car is let in. Flip the simulator below to "binary" and the lot shrinks to a single slot: that is a mutex.

Classic use: the producer-consumer problem

A producer puts items into a buffer of N slots and a consumer takes them out. We need three semaphores: empty (free slots, starts at N), full (filled slots, starts at 0) and mutex (protects the buffer itself, starts at 1).

semaphore mutex = 1, empty = N, full = 0;

// Producer                      // Consumer
while (true) {                    while (true) {
    produce_item();                 wait(full);     // any item to take?
    wait(empty);   // free slot?    wait(mutex);
    wait(mutex);                    item = remove_item();
    insert_item();                  signal(mutex);
    signal(mutex);                  signal(empty);  // one more free slot
    signal(full);  // one more item     consume(item);
}                                   }

Try it below. Speed up the producer and watch it block on wait(empty) when the buffer is full. Speed up the consumer and it blocks on wait(full) when the buffer is empty.

Pitfalls

  • Deadlock: if the producer calls wait(mutex) before wait(empty) and the buffer is full, it sleeps while holding the mutex, and the consumer can never get in to free a slot. Order of wait calls matters.
  • Forgetting a signal leaves other processes asleep forever; a stray extra signal can break mutual exclusion.
  • Priority inversion: a low-priority process holding a semaphore can indirectly delay a high-priority one.
  • Mutex vs binary semaphore: a mutex has an owner (only the locker may unlock); a binary semaphore can be signalled by any process, which makes it suitable for signalling between processes too.
✔Mutual exclusionWith a binary semaphore initialised to 1.
✔ProgressSignal always wakes a sleeper.
~Bounded waitingGuaranteed if the queue is FIFO; not with random wake-up.

Remember for the exam

  • Semaphore = integer + two atomic operations, wait and signal. Nothing else may touch it.
  • Binary semaphore initial value is 1 for mutual exclusion; counting semaphore starts at the number of resources.
  • Producer-consumer needs three semaphores: mutex = 1, empty = N, full = 0.
  • Semaphores are unstructured; misuse causes deadlock. Monitors were invented to fix this.

7Monitors

A monitor is a high-level language construct that bundles shared data, the procedures that operate on it, and the synchronization rules into one unit. The compiler guarantees that only one process can be active inside a monitor at any moment, so the programmer no longer writes wait(mutex) and signal(mutex) by hand.

Language-level toolHoare 1974, Brinch HansenBlocking

In real life: A doctor's clinic. Patients wait on chairs outside (the entry queue). Only one patient is in the cabin at a time (mutual exclusion, enforced by the clinic and not by patients). If the doctor says "you need a blood test first", that patient steps out and sits in a separate lounge (a condition queue) so the cabin is free for the next person. When the lab report arrives, the receptionist calls that patient back to the queue.

Parts of a monitor

  • Private shared data that can be accessed only through the monitor's procedures.
  • Procedures that run under automatic mutual exclusion.
  • Condition variables (for example notFull, notEmpty) with two operations. x.wait() releases the monitor and sleeps in the queue of x. x.signal() wakes one sleeping process; if nobody is waiting it does nothing (a signal is not remembered, unlike a semaphore's count).
monitor BoundedBuffer {
    int count = 0;                  // private data
    condition notFull, notEmpty;

    procedure put(item) {
        while (count == N) notFull.wait();   // buffer full: leave and sleep
        add(item);  count++;
        notEmpty.signal();                   // wake a sleeping consumer
    }

    procedure get() {
        while (count == 0) notEmpty.wait();  // buffer empty: leave and sleep
        item = remove();  count--;
        notFull.signal();                    // wake a sleeping producer
        return item;
    }
}

Notice there is no mutex anywhere in the code. In Java the same effect comes from synchronized methods together with wait() and notify().

Story in one paragraph

The lock variable is the obvious idea and it fails because check-and-set is not atomic. Strict alternation fixes exclusion but wastes turns (no progress). Peterson fixes both for two processes. Bakery extends the idea to N processes with tickets. Test and set stops fighting the problem in software and asks the hardware for an atomic step. Semaphores stop wasting CPU by putting waiters to sleep. Monitors stop programmers from misusing semaphores by making exclusion automatic.

Viva and interview questions

Why does the lock variable not guarantee mutual exclusion?
Because reading the lock and setting it are two separate instructions. A context switch between them lets two processes both read 0 and both enter.
Which requirement does strict alternation violate, and why?
Progress. A process in its remainder section can prevent another process from entering an empty critical section, because the turn variable still points to the absent process.
In Peterson's solution, what happens if both processes set their flags and then set turn?
The last writer of turn loses the tie and waits; the other process sees turn pointing to itself and enters.
Why does the bakery algorithm need the choosing array?
To stop a process from comparing itself against a ticket that another process is still computing. Without it two processes could each believe they hold the smallest ticket.
Why can test-and-set cause starvation?
When the lock is released, whichever spinning process executes TestAndSet first wins. The hardware does not order the competitors, so an unlucky process can lose indefinitely.
What does a negative semaphore value mean?
Its magnitude is the number of processes currently blocked on that semaphore (in the blocking implementation).
What is the difference between a counting and a binary semaphore?
A counting semaphore can take any non-negative count and manages a pool of identical resources; a binary semaphore is restricted to 0 and 1 and provides mutual exclusion.
How does a monitor's signal differ from a semaphore's signal?
A semaphore's signal is remembered in its counter even if nobody is waiting. A monitor's condition-variable signal is lost if no process is waiting.
