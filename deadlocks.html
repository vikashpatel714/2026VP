01 Definition

What exactly is a deadlock?

A deadlock is a situation where a group of processes are each waiting for a resource that another process in the same group is holding — and none of them will ever let go, because they too are waiting. The whole group freezes permanently. No crash, no error message. Just silence.

in everyday life

Two people meet in a narrow doorway, face to face. Each one steps aside to let the other pass — into the exact spot the other person just moved to. Both are being polite. Both are stuck. Neither will pass until one of them breaks the pattern.

inside a computer

Process A has locked File 1 and is waiting for File 2. Process B has locked File 2 and is waiting for File 1. Both requests are valid. Both processes are simply paused, forever, in a queue that will never be served.

02 Deadlock characterization

The four conditions that must all be true

In 1971, computer scientist Edward Coffman showed that a deadlock can only happen if all four of these conditions hold at the same time. Break even one of them, and the deadlock cannot form. This single idea is the foundation of every prevention strategy in the next section.

Condition 1 of 4

Mutual exclusion

A resource can be held by only one process at a time. If two processes could share it freely, there would be nothing to wait for.

Real life — Only one person can hold the office's single meeting-room key at a time.
Condition 2 of 4

Hold and wait

A process is allowed to keep the resources it already has while it waits for new ones. Waiting doesn't force it to give anything back.

Real life — You keep the fork in your hand while you wait for your neighbour to put down the knife.
Condition 3 of 4

No preemption

A resource can only be released voluntarily, by the process holding it. Nobody — not even the operating system — can just take it back mid-task.

Real life — Nobody can force you to hand over the meeting-room key just because someone else needs it.
Condition 4 of 4

Circular wait

There exists a closed chain of processes, where each one is waiting for a resource held by the next process in the chain.

Real life — The four-car gridlock from the top of this page — A waits on B, B waits on C, C waits on D, D waits on A.
03 Deadlock prevention

Design the system so a deadlock can't form

Prevention means restructuring how processes are allowed to ask for resources, so that one of Coffman's four conditions is never allowed to happen at all — not avoided at runtime, but ruled out by design.

Condition attackedHow it's brokenWhat it costs you
Mutual exclusion Make the resource shareable wherever possible — for example, a read-only file can be opened by many processes at once. Only works for resources that are genuinely safe to share; a printer or a write-lock still can't be.
Hold and wait Require every process to request all the resources it will ever need, in one go, before it starts running. Resources sit idle if a process asks for something early it only needs much later — poor utilization.
No preemption If a waiting process can't get a new resource, force it to release everything it's currently holding first. Work already done can be thrown away and repeated, wasting CPU time.
Circular wait Number every resource type, and force all processes to request resources in strictly increasing order. Programmers must plan requests around a fixed numbering scheme, which isn't always natural for the task.
04 Deadlock avoidance

The banker's algorithm: check before you say yes

Prevention is strict and wastes resources. Avoidance is smarter: it lets a process ask for anything, but before granting the request, the operating system simulates what would happen — and only grants it if the system would still be in a safe state afterwards.

the actual banker analogy

A bank has a fixed pool of cash and several customers, each pre-approved for a maximum loan. The banker will only approve a withdrawal today if enough cash would still be left to fully satisfy at least one customer — who can then repay their loan, freeing up cash for the next one, and so on for everybody.

the operating system version

Replace "customers" with processes, "cash" with resource instances (memory blocks, printers, file locks), and "loan" with the maximum a process declared it might ever need. A request is only granted if a full sequence exists in which every process can still finish.

A system is in a safe state if there is at least one order in which every process could run to completion, one at a time, even if each one first grabbed its full declared maximum. The algorithm below — the actual safety-check algorithm — searches for that order.

05 Deadlock detection

Let it happen, then find it with a graph

Some systems don't bother predicting the future at all — they let processes request resources freely, and instead periodically check whether a deadlock has already formed. They do this by drawing a resource-allocation graph and searching it for a cycle.

Solid arrow = "resource is assigned to process". Dashed arrow = "process is requesting resource".

Right now: P1 holds R1 and wants R2. P2 holds R2. Click the button above to make P2 also request R1 — and watch a cycle appear.

The detection algorithm is a plain graph search: reduce the graph by removing any process whose requests can currently be satisfied, and repeat. If processes remain that can never be reduced, they're deadlocked — which is exactly the same logic as a cycle existing in this simple case.

06 Recovery from deadlock

Detected it. Now what?

Detection only tells you a deadlock exists — the system still has to break it. In our gridlock analogy, this is the traffic officer who walks in and orders one car to reverse, even though that driver did nothing wrong.

Terminate a process

Kill one process in the cycle (releasing its resources) or, in the worst case, kill all of them. Killing one at a time and re-checking is gentler, but slower and requires picking a "victim" — usually the process with the least invested work.

Preempt a resource

Forcibly take a resource away from one process and give it to another, then roll that process back to a point before it held the resource. This needs the OS to track enough history to undo the process safely.

Rollback to a checkpoint

Periodically save a process's safe state. When a deadlock is found, rewind the offending process to its last checkpoint instead of killing it outright — it resumes from there once the resource is free.

07 Case study

How Oracle and MySQL actually handle this

Production databases can't afford to freeze, so they lean almost entirely on detection and recovery, done automatically, in milliseconds — deadlock avoidance in the strict Banker's-algorithm sense would require knowing every transaction's maximum resource need in advance, which is unrealistic for arbitrary SQL.

Consider two transactions updating two bank-account rows in opposite order:

-- Transaction 1
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = A;
-- ... pauses here ...
UPDATE accounts SET balance = balance + 100 WHERE id = B;
COMMIT;
-- Transaction 2, running at the same time
BEGIN;
UPDATE accounts SET balance = balance - 50  WHERE id = B;
-- ... pauses here ...
UPDATE accounts SET balance + 50  WHERE id = A;
COMMIT;

T1 locks row A, then wants row B. T2 locks row B, then wants row A. That's circular wait, formed by two ordinary UPDATE statements.

Press simulate to watch the wait-for graph form…

Both MySQL's InnoDB engine and Oracle Database maintain an internal wait-for graph of transactions and row locks. InnoDB checks it the instant a new lock request would create a cycle, and immediately rolls back whichever transaction has done the least work — that transaction's changes are undone and it receives error 1213: Deadlock found, while the other transaction proceeds untouched. Oracle does the same, but on a short timer (typically checking every few seconds), returning ORA-00060 to the losing session. In both engines, the losing application is expected to simply retry the transaction — the deadlock was between two individually correct statements, not a bug in either one.

The practical lesson both engines teach: application code that always locks rows in the same order — for example, always the lower account ID first — removes circular wait entirely, the same prevention idea from Section 03, applied by the programmer rather than the database.
