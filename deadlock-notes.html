Deadlock

Everyone is waiting. Nobody can move. Watch an operating system freeze itself, then rescue it.

A deadlock is a state where a set of processes is blocked forever because each one holds a resource and waits for a resource held by another process in the same set.

What is a deadlock?

A process uses a resource in three steps: request, use, release. If the resource is busy, the process waits. Deadlock appears when the waiting never ends. Resources can be physical (printer, tape drive, memory) or logical (file, lock, semaphore, database row).

Real-life example 1: Traffic gridlock. Four cars enter a crossing from four sides. Each car holds its own lane and needs the lane in front, which another car holds. Nobody can reverse, nobody can go forward.
Real-life example 2: One-lane bridge. Two vehicles meet in the middle. Each occupies half the bridge (holds) and needs the other half (wants). The only way out is for one vehicle to back off (preemption).
Real-life example 3: Fork and knife. Ravi holds the fork and waits for the knife. Meena holds the knife and waits for the fork. Both refuse to put anything down.
Real-life example 4: Databases. Transaction A locks the Accounts row and wants the Orders row. Transaction B locks Orders and wants Accounts. Databases such as MySQL detect this and abort one transaction.
Classic OS code example. Thread 1 runs lock(A); lock(B); while Thread 2 runs lock(B); lock(A);. If each grabs its first lock before the other grabs its second, both wait forever. The Dining Philosophers problem is the textbook version: five philosophers, five forks, and everyone picks up the left fork first.

Resource Allocation Graph (RAG)

A RAG has vertices for processes (circles) and resources (squares, dots = instances). A request edge P→R means P is waiting for R. An assignment edge R→P means R is allocated to P. The simulation above draws request edges as moving amber dashes and assignment edges as green lines.

  • No cycle in the graph: no deadlock.
  • Cycle and one instance per resource: deadlock for sure.
  • Cycle and several instances: deadlock possible, not certain (another process may release an instance).

Deadlock characterization

Deadlock can occur only if all four Coffman conditions hold at the same time. Tap each condition to switch it on or off and see what happens.

  1. Mutual exclusion: a resource can be used by only one process at a time (a printer cannot print two jobs at once).
  2. Hold and wait: a process holding at least one resource is waiting for more resources held by others.
  3. No preemption: a resource cannot be forcibly taken; only the holder can release it voluntarily.
  4. Circular wait: there is a chain P0→P1→...→Pn→P0 where each process waits for a resource held by the next.

Deadlock prevention

Prevention makes sure at least one Coffman condition can never hold. It is safe but restrictive.

Condition to breakHowDrawback
Mutual exclusionMake resources sharable (read-only files, spooling for printers).Impossible for truly non-sharable resources such as a mutex.
Hold and waitRequest all resources before starting, or request only when holding none.Low utilization and possible starvation.
No preemptionIf a request fails, release everything held and retry later; or take resources from a waiting process.Works only for states that can be saved (CPU registers, memory), not printers.
Circular waitGive every resource a number and force processes to request in increasing order.Ordering can be inconvenient and must be enforced by the programmer.
Real-life example. In the lock example, the fix is a rule: "always lock A before B". Now Thread 2 must also lock A first, so the circular wait disappears. Big software such as the Linux kernel documents lock ordering for exactly this reason.

Deadlock avoidance: the Banker's Algorithm

Avoidance needs advance information: each process declares its maximum need. The OS grants a request only if the system stays in a safe state.

Safe state: a safe sequence <P1, P2, ..., Pn> exists in which every process can finish using the currently free resources plus those released by earlier processes. Unsafe does not mean deadlocked; it means deadlock is possible. Deadlock is always unsafe.

Real-life example: a bank. A banker has a fixed cash pool and customers with credit limits. He lends more only if some order of repayment still lets every customer finish their business. That is why this is called the Banker's Algorithm.

Data structures (n processes, m resource types)

Available[m] free instances. Max[n][m] maximum demand. Allocation[n][m] currently held. Need = Max − Allocation.

Safety algorithm

  1. Work = Available; Finish[i] = false for all i.
  2. Find i with Finish[i] = false and Need[i] ≤ Work. If none, go to step 4.
  3. Work = Work + Allocation[i]; Finish[i] = true; go to step 2.
  4. If all Finish[i] are true, the state is safe; otherwise unsafe.

Resource-request algorithm for Pi with Request[i]

  1. If Request ≤ Need, continue; else raise an error (process exceeded its claim).
  2. If Request ≤ Available, continue; else Pi must wait.
  3. Pretend to allocate: Available −= Request, Allocation += Request, Need −= Request. Run the safety algorithm. Safe: grant. Unsafe: roll back and make Pi wait.

Deadlock detection

If the system uses neither prevention nor avoidance, it lets deadlock happen and then detects it. This is cheap in normal use but needs an algorithm and a recovery plan.

Single instance per resource: Wait-for Graph

Remove the resource nodes from the RAG and connect Pi→Pj if Pi waits for a resource held by Pj. A cycle in the wait-for graph means deadlock. Cycle detection costs O(n²). In the simulation above, P1→P2→P1 is the wait-for cycle.

Multiple instances: detection algorithm

It is the safety algorithm, but it uses the current Request matrix instead of Need.

  1. Work = Available. Finish[i] = false if Allocation[i] ≠ 0, otherwise true.
  2. Find i with Finish[i] = false and Request[i] ≤ Work.
  3. Work += Allocation[i]; Finish[i] = true; repeat.
  4. Any Finish[i] = false means Pi is deadlocked.

Complexity is O(m × n²).

When to run it?

After every request that cannot be granted (early detection, high overhead), or periodically, or when CPU utilization drops below a threshold (for example 40%).

Real-life example. PostgreSQL waits about one second on a lock, then checks its wait-for graph. If it finds a cycle, it aborts one transaction with the error "deadlock detected". Most desktop operating systems mostly ignore rare deadlocks and let the user kill the frozen app; this is called the Ostrich algorithm.

Recovery from deadlock

1. Process termination

  • Abort all deadlocked processes: breaks the cycle at once but wastes a lot of computation.
  • Abort one at a time: run detection after each kill. Less waste, more overhead.

Choose the victim by: priority, time already computed and time remaining, resources held, resources still needed, whether the process is interactive or batch, and how many processes must be terminated.

2. Resource preemption

  • Select a victim with minimum cost.
  • Rollback: return the victim to a safe earlier state (checkpoint) and restart it from there.
  • Starvation: the same process may be picked again and again. Include the number of rollbacks in the cost so it eventually stops being the victim.
Real-life example. When the one-lane bridge jams, one driver reverses (rollback), the other crosses, and then the first driver tries again. Task Manager's "End task" and a database transaction abort are the same idea.
